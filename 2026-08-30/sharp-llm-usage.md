## 今日の一言
LLM活用の鋭さは「よいプロンプト」単体から、失敗・検証・文脈分離をワークフロー化して、人間が安心して判断できる形にする方向へ寄っています。

## トップ5

### 1. Rudder: 仕様をテストで測る、後付けSpec-Driven Development
- 出典: GitHub / Hacker News経由で確認
- 日付: 2026-08-26（Hacker News掲載日）
- リンク: https://github.com/RudderCode/Rudder
- 要約: RudderはClaude CodeやCodex向けのローカルプラグインで、セッション履歴や既存specから仕様を生成し、その仕様に紐づく単体テストを作らせることで「仕様がどれだけ包括的か」を検証する。長いspecを最初から書く負担を避けつつ、エージェントの推測を減らすために質問で仕様を詰めていく点が実践的です。
- なぜ面白いか:
  - 技術: プロンプト履歴、仕様文書、単体テスト、カバレッジを同じループに入れ、LLM出力の正しさを「要求とテストの対応関係」として検証しようとしている。
  - 人文: これはAIに仕事を任せるというより、人間の曖昧な依頼を監査可能な契約へ変換する道具です。創造的な会話の流れを捨てずに、後から説明責任を回復する設計が面白い。

### 2. “How to Claude Like Anthropic”: 多数エージェント運用と手動検証ループの対比
- 出典: Hacker News Ask HN
- 日付: 2026-08-22
- リンク: https://news.ycombinator.com/item?id=49396175
- 要約: Anthropic社内の例として「2人のリードエージェント、複数のPM/Tech Lead、各プロジェクト5〜10のICエージェント」という大規模運用が引用され、それに対して投稿者はplan/spec作成、別セッションによるPRレビュー、元セッションへの修正依頼、E2Eテスト計画という手動寄りのClaude Code運用を共有している。最も鋭い点は、完全自動化への憧れと、人間がレポートを読んで安心する必要性が同時に語られていることです。
- なぜ面白いか:
  - 技術: 実装セッション、レビューセッション、修正セッション、E2E確認を分離し、同じ変更を複数の役割から検証するワークフローになっている。
  - 人文: 「自動化されていないから遅い」のではなく、「読める報告があるから信頼できる」という感覚が重要です。LLM時代の生産性は、人間がどこで安心を得るかという心理設計にも左右されます。

### 3. CritICL: 小さいモデルの失敗を、強いモデルの推論コンテキストに変える
- 出典: arXiv
- 日付: 2026-08-27
- リンク: https://arxiv.org/abs/2608.27455v1
- 要約: CritICLは、同一ファミリー内の弱いモデルが示す失敗モードを抽出し、それを批判的なin-context例として強いモデルの推論時に使う手法。多数回サンプリングや外部検証に頼りすぎず、少ない生成回数・低いトークンコストで標準ICLを上回る性能を狙っている。
- なぜ面白いか:
  - 技術: 「失敗例」を捨てずに構造化し、動的または静的な批評コンテキストとして再利用することで、推論時スケーリングのコストを下げる。
  - 人文: 人間の熟達も失敗の蓄積から生まれますが、この論文はそれをLLMの文脈設計へ移植している。失敗を隠すのではなく、共同作業の教材に変える発想が実務にも応用しやすい。

### 4. NIS-Agent: Deep Researchの「自分の前提に引っ張られる」問題を文脈分離で抑える
- 出典: arXiv
- 日付: 2026-08-27（v2更新）
- リンク: https://arxiv.org/abs/2608.23045v2
- 要約: “From Inertia to Objectivity”は、検索エージェントが自分で立てたクエリ・計画・中間結論を後続判断で過大評価する「inertia bias」を測定し、Webページ選別と最終回答検証の場面で文脈を分離するNIS-Agentを提案している。GAIAなどで競争力を保ちながら、ベースライン比でトークンコストを33%削減したと報告されている。
- なぜ面白いか:
  - 技術: エージェントの行動履歴を全部コンテキストに入れるのではなく、判断が歪みやすい局面だけ履歴を隔離して検証精度とコストを改善する。
  - 人文: 人は自分が言ったことに縛られますが、LLMエージェントも同じように「自分の物語」に巻き込まれる。よいLLM活用とは、記憶を増やすだけでなく、忘れさせる設計でもあると示している。

### 5. Anchoring Bias in LLM-as-a-Judge: 評価メタデータが検証者を汚染する
- 出典: arXiv
- 日付: 2026-08-26
- リンク: https://arxiv.org/abs/2608.25869v1
- 要約: LLM-as-a-Judgeに過去スコア、試行番号、改訂情報などのメタデータを与えると、評価がそのアンカーへ体系的に引き寄せられることを大規模評価で示した研究。反復改善パイプラインで「前回スコア」を何気なく渡す設計が、独立した検証を損なう可能性を具体的に警告している。
- なぜ面白いか:
  - 技術: 検証用LLMに与えるコンテキストの中でも、 prior score や revision framing が評価分布を変えるため、評価者プロンプトは実装者プロンプト以上に情報衛生が必要になる。
  - 人文: 評価は中立に見えても、制度や履歴に引っ張られます。LLM評価器のバイアスは、人間社会の採点・査読・人事評価にあるアンカリング問題を技術システム内に再現している。
