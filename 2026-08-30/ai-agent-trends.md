### 1. Terminal-Bench-Science 0.1: 研究ワークフローでAIエージェントを評価
- 出典: Web / Hacker News掲載記事
- 日付: 2026-08-28
- リンク: https://www.terminal-bench-science.ai/announcement
- 要約: Terminal-Bench-Science 0.1 は、Stanford University と Terminal-Bench チームが研究者の実務から作った70タスクで、AIエージェントの科学研究ワークフロー能力を評価するベンチマークです。公開ページでは Claude Opus 5 + Claude Code が30.0%、GPT-5.6 Sol + Codex が22.4%という解決率も示され、まだ「研究助手」としては難所が多いことが見えます。
- なぜ面白いか:
  - 技術: コーディング単体ではなく、科学者が実際に行う端末ベースの検証可能な作業をタスク化しており、エージェント評価の重心を現実の研究実践へ移しています。
  - 人文: 研究者自身がベンチマークを作る点が重要で、AIの進歩を「ベンダーが測りやすい能力」ではなく「科学コミュニティが必要とする能力」で測ろうとしています。人間の判断が残る領域、つまり問いの設定・仮説形成・解釈・伝達をどう守るかという科学哲学的な論点も含みます。

### 2. Concord MCP: Claude Code、Codex、Cursorなどを会話させるローカルファースト協調層
- 出典: GitHub / Hacker News
- 日付: 2026-08-27（HN掲載）
- リンク: https://github.com/Get-Concord-AI/concord-mcp
- 要約: Concord MCP は、Claude Code、Codex、Cursor、Gemini CLI、Grok Build などのコーディングエージェントが、作業範囲の衝突検知、メッセージ交換、意思決定共有、タスク引き継ぎを行えるMCPサーバです。READMEでは、同じファイルを複数エージェントが編集しようとしたときに所有権を調整するデモが説明されています。
- なぜ面白いか:
  - 技術: MCPを「外部ツール接続」だけでなく、複数ハーネス間の共有作業状態・排他制御・ハンドオフ基盤として使っている点が実践的です。
  - 人文: これはAI同士の協働というより、人間チームの暗黙的な段取りや縄張り調整をエージェント世界へ移植する試みです。ソフトウェア開発における“誰が何を担当しているか”という社会的秩序が、プロトコルとして明文化されつつあります。

### 3. WikiSkill: エージェント経験を永続知識にまとめてスキル進化へつなげる
- 出典: arXiv
- 日付: 2026-08-27
- リンク: https://arxiv.org/abs/2608.27454
- 要約: WikiSkill は、エージェントの実行経験、蓄積知識、実行可能スキルを分離し、経験を継続的にwikiへ統合してからスキル更新に使うフレームワークです。論文概要では、永続知識の蓄積がスキル進化に重要であり、進化したスキルがモデル間・モデルファミリー間で転移することも示されています。
- なぜ面白いか:
  - 技術: 単発の会話ログではなく、経験を再利用可能な知識基盤へ圧縮してスキルを更新するため、エージェント運用における記憶・技能・再現性の分離設計として参考になります。
  - 人文: 「経験が技能になる」過程をAIで制度化する研究であり、徒弟制や組織学習に近いテーマです。誰の経験が標準化され、どの知識が長く残るのかという文化的・権力的な問いも生まれます。

### 4. Do User-Authored Permission Policies Improve Protection Against AI Agent Overreach?: ユーザー作成ポリシーは過剰実行を十分に防ぐか
- 出典: arXiv
- 日付: 2026-08-27
- リンク: https://arxiv.org/abs/2608.27443
- 要約: この研究は、非専門家ユーザーが「allow / ask / never」の自然言語ポリシーでAIエージェントの行動を事前制御できるかを、113人の参加者で検証しています。結果として、ポリシー方式は実行時プロンプトを減らす一方、HITLや自動レビューより過剰実行のブロック率が低く、多くの参加者が結局「ask」を選んで判断を後回しにしたと報告されています。
- なぜ面白いか:
  - 技術: エージェント権限を静的ルールに落とすだけでは安全性が自動的に上がらず、分類モデル、UI、承認フロー、ユーザー心理を一体で設計する必要があることを示しています。
  - 人文: 自由に選べることと、将来の自分を拘束するルールを作ることは別物だと分かります。AIエージェントの安全性は、単なるアクセス制御ではなく、人間が責任・不安・便利さをどう交渉するかという倫理の問題でもあります。

### 5. agentd: 複数コーディングエージェントのフックを一つのローカルデーモンで守る
- 出典: GitHub
- 日付: 2026-08-29（GitHub更新確認）
- リンク: https://github.com/macrox-pro/agentd
- 要約: agentd は、Claude Code、Cursor、Codex、Gemini CLI、OpenCode、Kimi Code などのコーディングエージェントとフック処理の間に入り、ローカルのユーザーレベルデーモンとしてポリシー適用、同期・非同期パイプライン、観測をまとめるツールです。READMEでは、プロバイダごとのフック互換性やセッション統計、Claude CodeやCodexなどの調査スナップショットに基づく設計が説明されています。
- なぜ面白いか:
  - 技術: 各エージェントごとに散らばるhook/permission/observabilityを一段抽象化し、ローカルで一貫したガードレールを置こうとしている点が、エージェント運用の現実的な方向性です。
  - 人文: エージェントを“野良の便利ツール”ではなく、職場の監査・習慣・リスク管理の中に置く動きです。人間が安心して任せるためには、能力よりも「見えること」「止められること」「後で説明できること」が信頼の条件になります。
