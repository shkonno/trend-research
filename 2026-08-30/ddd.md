## 今日の一言

DDDは「AIに設計を丸投げする方法」ではなく、LLM/エージェントを使ってドメイン言語・境界・意思決定を可視化し、人間の合意形成を強くする方向に面白さが出ています。

## トップ5

### 1. Towards Standardized Evaluation in Automated Domain Modeling: Introducing a Benchmark
- 出典: arXiv
- 日付: 2026-08-15（直近14日よりやや古いが重要）
- リンク: https://arxiv.org/abs/2608.15255
- 要約: 自然言語記述からドメインモデルを生成する自動モデリング手法を比較するため、既存のGolden UML Modelsetなどを組み合わせたベンチマークを提案しています。LLM駆動の戦略も評価対象に入り、DDDの「モデル化」を測定可能な研究課題として扱っている点が新しいです。
- なぜ面白いか:
  - 技術: LLMで作ったドメインモデルを雰囲気ではなく参照モデルとメトリクスで比較する土台を作っており、AI時代のDDD品質保証に直結します。
  - 人文: DDDのモデルは本来、組織の会話と合意の産物ですが、この研究はその一部を「評価可能な成果物」に変換しようとしています。測れるものだけが重要になる危険もある一方、設計議論の透明性を上げる可能性があります。

### 2. DDD-Enforcer: SRS-grounded Domain-Driven Design enforcement for Python
- 出典: GitHub / IEEE Xplore掲載研究の実装リポジトリ
- 日付: 2026-08-13更新（直近14日より古いが関連度が高い）
- リンク: https://github.com/barandincoguz/DDD-Enforcer
- 要約: 要求仕様書から型付きのDDDモデルを抽出し、PythonコードをAST解析・import topology・RAG付きトレーサビリティで検査して、VS Code診断として設計逸脱を表示するツールです。READMEでは、マルチステージLLM orchestrationと決定論的検証を組み合わせる構成が説明されています。
- なぜ面白いか:
  - 技術: DDDを「設計ワークショップの成果」から「継続的に検査されるアーキテクチャ制約」へ押し出しており、AIエージェントによる実装暴走へのガードレールになります。
  - 人文: 仕様書・コード・診断をつなぐことで、設計判断の責任を個人の記憶ではなく共有された証跡に移せます。これは組織文化としてのDDD、つまり「言った/言わない」を減らす実践としても意味があります。

### 3. LLM_Ontology_DDD: Hybrid LLM–Ontology Approach for Ubiquitous Language
- 出典: GitHub
- 日付: 2026-08-12作成・更新（直近14日より古いが関連度が高い）
- リンク: https://github.com/BlayTeuR/LLM_Ontology_DDD
- 要約: ユビキタス言語の構築と意味的衝突の解消に、LLMとオントロジーを組み合わせることを掲げたリポジトリです。READMEは短いものの、DDDの語彙問題を単なるプロンプト生成ではなく、意味体系の整備として扱っている点が注目です。
- なぜ面白いか:
  - 技術: LLMの柔軟な言語処理とオントロジーの厳密な意味制約を合わせる発想は、ユビキタス言語の曖昧さ検出や用語統一に向いています。
  - 人文: ユビキタス言語はチームの「方言」を作る営みであり、そこには権限、職能、歴史的経緯が入り込みます。AIが用語衝突を指摘するなら、それは辞書作成ではなく、組織内の認識差を安全に表面化するファシリテーションになります。

### 4. faceto: typed fileからLLMと考えるイベントストーミングボードへ
- 出典: GitHub / ドキュメントサイト
- 日付: 2026-08-07更新・2026-08-11 push（古いが重要）
- リンク: https://github.com/bastien-gallay/faceto
- 要約: 型付きファイルからHTML/SVGのイベントストーミングボードを生成し、クリックした要素にメモを書いて次のLLMセッションでモデル調整に使う、というワークショップ支援ツールです。イベントストーミングを第一形式とし、将来的にコンテキストマップやBounded Context Canvasへ広げる方向が示されています。
- なぜ面白いか:
  - 技術: AIコーディング前のモデルをファイル・可視化・対話メモとして往復させるため、プロンプトだけに閉じない設計ループを作れます。
  - 人文: イベントストーミングの価値は付箋そのものではなく、その場で人々が驚き、衝突し、合意する過程にあります。facetoのような道具は、リモート/非同期のチームでもその社会的プロセスを残しやすくします。

### 5. Automating Domain-Driven Design: Experience with a Prompting Framework
- 出典: arXiv
- 日付: 2026-03-27（古いが、AI/LLM時代のDDD設計論として継続的に重要）
- リンク: https://arxiv.org/abs/2603.26244
- 要約: ユビキタス言語の確立、イベントストーミングのシミュレーション、境界づけられたコンテキストの識別、集約設計、技術アーキテクチャへの写像という5段階を、構造化プロンプトで支援する経験報告です。論文の要旨では、前半のステップは有用だが、後半では小さな誤りが蓄積して実用性を損なうとされています。
- なぜ面白いか:
  - 技術: LLMはDDDの全自動化よりも、語彙・イベント・境界の初期整理を助ける「sparring partner」として使うほうが現実的だと示しています。
  - 人文: これはAI導入の成熟した態度を示す事例です。専門家の判断を置き換えるのではなく、議論すべき論点を早く可視化し、人間がトレードオフを引き受ける余地を残しています。
