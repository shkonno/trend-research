## 今日の一言

Harness engineering は「モデル単体の賢さ」から、仕様・実行・評価・記憶・失敗調査を包む運用レイヤーの設計へと急速に重心が移っている。

## トップ5

### 1. Tenet: 長時間自律開発のためのクロスプラットフォーム・エージェントハーネス

- 出典: GitHub リポジトリ
- 日付: 2026-08-25 更新（作成: 2026-04-08）
- リンク: https://github.com/JeiKeiLim/tenet
- 要約: Tenet は Claude Code / OpenCode / Codex を対象に、仕様インタビュー、DAG 分解、ジョブ実行、独立した 3 クリティック評価を組み合わせて 12 時間以上の自律開発サイクルを支える TypeScript 製ハーネス。GitHub のトピックにも `harness-engineering` が付いており、この分野をかなり明示的に名乗っている。
- なぜ面白いか:
  - 技術: 単発プロンプトではなく、仕様、依存グラフ、モデル能力に応じた計画調整、評価者によるゲートを一つの制御ループにまとめている点が実践的。
  - 人文: 「開発者がAIに命令する」よりも「組織的な作業制度をAIの周囲に作る」方向で、ソフトウェア開発の権限・責任・レビュー文化を再設計している。長時間エージェントをどう信頼するかという問いを、人格ではなく制度設計として扱っているのが面白い。

### 2. OMK: AIアプリの知識変更を evidence-backed にする評価・観測レイヤー

- 出典: GitHub / npm 対応リポジトリ
- 日付: 2026-08-30 更新（作成: 2026-03-24）
- リンク: https://github.com/lizhiyao/oh-my-knowledge
- 要約: OMK はプロンプト、RAG、スキル、エージェント、ワークフローの変更を、同じモデル・同じ評価サンプルで比較し、知識アーティファクトの差分だけを測る評価・観測フレームワーク。README とトピックでは Claude Code、DeepSeek Harness、Codex などの実行器対応が示されている。
- なぜ面白いか:
  - 技術: ハーネスを「実行の包み」だけでなく、知識変更のバージョン管理・評価・リリース判定の基盤として扱っている。
  - 人文: AIシステムの改善が「なんとなく良くなった」という雰囲気に流れやすい中で、証拠に基づく変更文化を作ろうとしている。これはチーム内の説明責任や、現場での合意形成を支える社会的インフラでもある。

### 3. Eval Investigation Skill: 評価失敗の原因をハーネス非依存で調査するスキル

- 出典: GitHub リポジトリ
- 日付: 2026-08-29 作成・更新
- リンク: https://github.com/Akshata4/eval-investigation-skill
- 要約: AIエージェント評価で低スコアが出たときに、何が・どの頻度で・なぜ失敗したのか、また責任がエージェント、ツール、採点器、データセットのどこにあるのかを調査するためのプレーンテキスト方法論。Claude Code、Codex CLI、Cursor、Windsurf、Aider など任意のハーネスにシステムプロンプトやスラッシュコマンドとして渡せる設計になっている。
- なぜ面白いか:
  - 技術: 低スコアを即「モデルが悪い」と解釈せず、評価系・ツール系・データ系まで分解して調べる root-cause investigation をハーネスの部品として位置づけている。
  - 人文: 失敗の責任を単一の主体に押しつけない姿勢がある。AIエージェント時代の品質保証では、失敗を罰するよりも、失敗を読解し共有可能な知識へ変える文化が重要になる。

### 4. AI Coding Harness, MCP & LSP Benchmark Suite: コーディングハーネスをCIで比較するベンチマーク

- 出典: GitHub リポジトリ
- 日付: 2026-08-22 更新（作成: 2026-08-21）
- リンク: https://github.com/Heretek-AI/harness-benchmark
- 要約: Claude Code、Gemini CLI、OpenCode、DeepSeek 系、Antigravity などの AI coding harness と、MCP サーバー、LSP 診断、プラグインを CoderEval / Terminal-Bench 系タスクで比較する Python 製ベンチマーク兼 GitHub Action。行列実行、アブレーション、MCP/LSP まで含めた「開発環境ごと測る」方向が特徴。
- なぜ面白いか:
  - 技術: モデルやCLI単体ではなく、MCP、LSP、プラグイン、診断環境まで含む複合ハーネスをCIで再現可能に比較しようとしている。
  - 人文: 開発者体験は見えにくい道具の組み合わせでできているため、ハーネス比較は「どのAIが賢いか」から「どの作業環境が安全で納得できるか」へ議論を移す。ツール選定の政治性を、測定可能な形に下ろす試みとも読める。

### 5. Michele — AI Work System Builder: 日本語説明を含む Claude Code 向け業務ハーネス生成プラグイン（古いが関連性高）

- 出典: GitHub リポジトリ
- 日付: 2026-07-07 更新（直近14日より古いが、日本語コミュニティ接点として重要）
- リンク: https://github.com/blackrabbit74/michele-ai-work-system-builder
- 要約: Michele（ミシェル）は、ユーザーが本当に専用AI業務システムを作るべきかを見極め、必要な場合に Claude Code 上でスキル、サブエージェント、ルーティング、フック、記憶方針、行動評価、導入文書を含む installable な業務ハーネスを設計・生成するプラグイン。README には日本語のクイックスタートと説明が含まれている。
- なぜ面白いか:
  - 技術: ハーネスを単なる評価器ではなく、チーム固有の仕事の進め方をパッケージ化する「業務OS」として生成する点が特徴。
  - 人文: 日本語で「本当に作るべきか」から始める設計は、AI導入を自動化の誘惑ではなく、組織の目的確認として扱っている。ハーネスが職場文化を固定化も改善もできるという、社会技術的な緊張がよく表れている。
