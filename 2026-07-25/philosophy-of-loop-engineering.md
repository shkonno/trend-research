## 今日の一言
ループエンジニアリングは「AIに何を言うか」から「観察・評価・修正が回り続ける制度をどう設計するか」へ移り、サイバネティクスと実践知の語彙で再解釈され始めています。

### 1. Prompt Engineering → Context Engineering → Loop Engineering → Graph Engineering という移行論
- 出典: X投稿（@TheYotg）
- 日付: 2026-07-24
- リンク: https://x.com/TheYotg/status/2080599881278791943
- 要約: X検索では、ループを単発の自己修正機構としてではなく、生成・評価・意思決定・人間へのエスカレーションを分ける「グラフ」へ発展させる議論が目立ちました。同じ主体が作成と評価を兼ねると局所最適やトークン浪費に陥るため、型付き状態、反復上限、独立したレビュー経路が重要だという実践的論点です。
- なぜ面白いか:
  - 技術: 自律エージェントを無制限ループではなく、制御ロジック・評価者・停止条件を分離したワークフローとして設計する指針になります。
  - 人文: これは「観察者が自分自身を観察する」第二次サイバネティクスの問題を、AI開発の現場語彙に翻訳したものです。認識論的には、正しさを自己申告に任せず、複数の証言・検証・制度的手続きを通して成立させる発想へ近づいています。

### 2. 日本語圏での「ループエンジニアリング」概念の結晶化
- 出典: X投稿（@hawkymisc）
- 日付: 2026-07-24
- リンク: https://x.com/hawkymisc/status/2080525772738211962
- 要約: 日本語X検索では、#AIDevDay や OpenClaw / Crabfleet 周辺の議論を契機に「ループエンジニアリング」という語が、ハーネス、AI Slopのトリアージ、自己改善する開発プロセスと結びついて語られていました。単なるプロンプト技術ではなく、AIエージェントが失敗を見つけ、測り、作り直す開発環境そのものを設計するという文脈です。
- なぜ面白いか:
  - 技術: MCP、レビューエージェント、TDD、静的解析、ブラウザ実検証などを組み合わせ、CIが通るだけではなく「実際に動く」ことをループ内で確認する方向を示しています。
  - 人文: 日本語圏の議論では、実践者が現場で生んだ言葉として概念が育っている点が重要です。哲学でいう実践知は、先に理論があり後から応用されるのではなく、失敗処理・手戻り・共同作業の中で語彙化されます。

### 3. IBM「What is loop engineering?」が企業向け定義を提示
- 出典: Web記事（IBM Think）
- 日付: 2026-07-17
- リンク: https://www.ibm.com/think/topics/loop-engineering
- 要約: IBMはループエンジニアリングを、AIエージェントが act / observe / decide / iterate を繰り返し、ユーザー定義のゴールへ最小限の人間介入で近づくエージェント型ワークフロー設計として説明しています。開発者の役割は、逐次プロンプトを書く人から、目的・観察・判断・反復の条件を設計する人へ変わる、という整理です。
- なぜ面白いか:
  - 技術: 企業導入で必要な責任境界、ゴール設定、観察可能性、停止条件を含むため、流行語を運用設計へ落とす入口になります。
  - 人文: 「最小限の人間介入」は人間の不在ではなく、人間がどこで基準を与えるべきかを問い直します。これは自律性を機械の属性としてではなく、人間・制度・測定基準を含む関係として捉える見方です。

### 4. LangChain「The Art of Loop Engineering」：観測と評価を中核に置く古いが基礎的な記事
- 出典: Web記事（LangChain Blog）
- 日付: 2026-06-16（14日より古いが、現在の議論の基礎として関連）
- リンク: https://www.langchain.com/blog/the-art-of-loop-engineering
- 要約: LangChainの記事は、ループエンジニアリングを長時間動くエージェントの改善技法として扱い、観測、評価、サンドボックス、改善サイクルをプロダクト群とも接続しています。X上の直近議論が「グラフ」や「評価者の分離」へ進んでいる一方で、その前提となる観測可能性と評価基盤を示す資料です。
- なぜ面白いか:
  - 技術: LangSmith / LangGraph 的な実装文脈では、ループは抽象理念ではなく、トレース、評価、デプロイ、安全なコード実行と一体の運用問題になります。
  - 人文: 哲学的には、これは経験論的な学習観に近く、知識は一度の推論ではなく、失敗記録と再検証を通して蓄積されます。ループの「芸術」は、完全自動化ではなく、何を観察可能にするかを選ぶ判断の芸術でもあります。

### 5. LOGOS: A Living Logic for AI Agent Teams That Evolve With Humans
- 出典: arXiv（2607.10878v1）
- 日付: 2026-07-12
- リンク: http://arxiv.org/abs/2607.10878v1
- 要約: LOGOSは、AIエージェントがツールを使い、委任し、経験から学び、自身の将来の振る舞いを形作る成果物を変更する時代に、「誰がその変化を統制するのか」を問う論文です。文書・API・人間の指示などをバージョン管理された agent packs にまとめ、イベントトレースと fail-closed なガバナンスで自己進化を扱う枠組みを提案しています。
- なぜ面白いか:
  - 技術: ループをプロンプト改善ではなく、権限、テスト、ポリシー、監査可能なイベント履歴を含む進化管理レイヤーとして扱っています。
  - 人文: 「生きた論理」という表現は、固定された規則ではなく、人間と機械の共同実践の中で規則が更新されるというプラグマティズム的な発想に近いものです。自己改善するAIの哲学的核心は、賢くなることそのものではなく、変化を誰が正当化し、どの記録に基づいて信頼するかにあります。
