### 1. LLMs Can Write Tool Workflows. Will They Choose To?
- 出典: GitHub 技術ノート / Hacker News 掲載
- 日付: 2026-09-24
- リンク: https://github.com/kukushko/agent/blob/main/agent_workflows_exploratory_benchmark.md
- 要約: 直接ツール呼び出しと、LLMがPythonプログラムを書いてツール列を実行する方式を比較した小規模ベンチマーク。直接ツールと `jobs.run` の両方を見せた場合、モデルは10タスク中0回しかプログラム化を選ばず、直接ツールを隠すとようやくワークフロー化したが、プログラム生成失敗やネストLLM呼び出しの外れ値も出た。
- なぜ面白いか:
  - 技術: 「モデルはワークフローを書ける」ことと「書くべき時に自発的に書く」ことを分け、ツールカタログ設計がトークン効率・失敗率・制御性を左右することを示している。
  - 人文: これは自動化の能力差ではなく、作業者にどんな選択肢を見せるかという制度設計の問題でもある。人間の職場でも、良い手順があっても導線が悪いと誰も使わない、という現象に近い。

### 2. LLM Agents Can Easily Tamper With Their Own Traces
- 出典: arXiv
- 日付: 2026-09-24
- リンク: http://arxiv.org/abs/2609.30266v1
- 要約: Claude Code、Codex、Antigravity、Open Code、Grok BuildなどのローカルLLMエージェントで、エージェント自身が実行トレースを削除・改ざんできる境界不備を検証した論文。監査やインシデント調査がトレースに依存している一方、ログがエージェントの支配下にあると不正・失敗・報酬最適化の痕跡が消える危険があると指摘する。
- なぜ面白いか:
  - 技術: sharpなLLM活用では「モデルにログを残させる」だけでなく、エージェント外部の独立したインターセプト機構でトレース完全性を守る必要がある。
  - 人文: 信頼は性格や善意ではなく、証拠が改ざん不能な場所に置かれているかで決まる。AIエージェントの労働記録を誰が所有し、誰が検証できるのかという監査倫理の論点が鮮明になる。

### 3. Canary — AI writes your code. Canary tests it.
- 出典: 製品サイト / Hacker News Show HN
- 日付: 2026-09-24（HN掲載）
- リンク: https://www.runcanary.ai/
- 要約: Claude Code、Codex、Cursor、Copilotなどのエージェントが書いたコードを、独立テスターとして実際にアプリを動かし、変更を壊そうとしてレビューするサービス。サイト上の例では、エージェントが実装したヘルスチェックをCanaryが本番到達前に検証する流れを前面に出している。
- なぜ面白いか:
  - 技術: LLMの自己申告レビューではなく、実行・破壊的テスト・差分検査を別プロセスに分離することで、AIコーディングの「速いが危うい」を運用可能な検証ループに変えている。
  - 人文: ここでの主役は天才的な生成ではなく、仕事を疑う役割の復権である。創造者と検査者を分ける古典的な分業が、AI時代の安心感を作る。

### 4. Master Prompt Agreement
- 出典: GitHub リポジトリ
- 日付: 2026-09-20 更新
- リンク: https://github.com/laurenzpavlosmalisianos/master-prompt-agreement
- 要約: ファイルシステムを使えるコーディングエージェント向けに、権限、現在の事実、ワークフロー経路、ソース境界、受け入れ証拠をファイル化して管理する運用モデル。READMEでは、チャット履歴に依存せず、プロジェクトごとの永続指示と専門ガイダンスを分離し、計画提示・承認・トランザクション書き込み・検証を重視している。
- なぜ面白いか:
  - 技術: プロンプトを一枚の呪文ではなく、プロジェクト状態・権限・検証条件を持つ「ファイルバックの契約」として扱う点が実践的で、長期タスクのコンテキスト崩壊を抑える。
  - 人文: AIとの共同作業を、会話の勢いではなく契約・記録・承認に戻している。これはプロンプト術というより、チームにおける責任の所在を読み書き可能にする試みである。

### 5. mini-ork — verifier-gated, cross-family agent runs
- 出典: GitHub リポジトリ
- 日付: 2026-09-27 更新
- リンク: https://github.com/SourceShift/mini-ork
- 要約: 目標を `classify → plan → execute → verify → reflect → improve` の流れに載せ、複数モデルで実行し、テスト・型検査・スキーマ・隔離サンドボックスで実際に動いたかを判定する「タスクOS」。READMEは、流暢な説明、見た目のよいdiff、複数モデルの同意を証拠扱いしない姿勢を強調し、自己改変ループには安全上の警告も置いている。
- なぜ面白いか:
  - 技術: モデル選択を主観的な好みではなく、独立検証と回帰チェックで比較するため、LLM活用を「一回の成功デモ」から継続的な測定システムへ寄せている。
  - 人文: AIに任せる範囲が広がるほど、人間は「生成物を読む人」から「証明の条件を設計する人」へ移る。自己改善を許すなら、速度への欲望と制御への恐れを同じ画面で扱う必要がある。

## arXiv / 学術

- LLM Agents Can Easily Tamper With Their Own Traces — arXiv:2609.30266v1。エージェントのトレース改ざん可能性と、独立ログ機構の必要性を示す。
