## トップ5

### 1. The harness is all you need (mostly)
- 出典: GitHub Blog
- 日付: 2026-07-27（ページ上では2026-07-28更新）
- リンク: https://github.blog/ai-and-ml/github-copilot/the-harness-is-all-you-need-mostly/
- 要約: GitHub Copilotを題材に、プロトタイプ、計画、実装、レビューを既存機能の「ハーネス」として使い切る実践ワークフローを示す記事。新しいMCPや裏技プロンプトを追うより、曖昧な依頼を計画で分解し、同じモデル・推論設定を保ってキャッシュや会話文脈を活かす、という地味だが強い使い方が中心になっている。
- なぜ面白いか:
  - 技術: LLM活用の性能差をモデル単体ではなく、計画、文脈保持、レビュー、UI/IDEの足場を含む「実行環境の設計」として捉えている。
  - 人文: 「AIを使いこなす」とは秘伝の呪文を持つことではなく、作業の順序や問いの立て方を鍛える職人的実践だと読み替えられる。ツール熱に疲れた開発者へ、注意深い作業習慣そのものが価値になるという落ち着いたメッセージがある。

### 2. Don’t Take This Out of Context: Feeding Your LLM Exactly What It Needs
- 出典: Malt Engineering / Medium
- 日付: 2026-07-30（HN掲載は2026-08-03として確認）
- リンク: https://blog.malt.engineering/dont-take-this-out-of-context-feeding-your-llm-exactly-what-it-needs-0db8a86d2151
- 要約: LLM APIはステートレスであり、会話、RAG、MCP、メモリ、ツールが毎回コンテキストに流れ込むため、「少なすぎると幻覚、多すぎるとコスト・遅延・注意散漫」が起きると整理する実践ガイド。選択的検索、progressive disclosure、編集、ブランチング、サブエージェント、ガードレールとセキュリティを、作る側・使う側の両方から説明している。
- なぜ面白いか:
  - 技術: プロンプト単体の調整から、入力文脈を選択・編集・分岐・隔離するコンテキストエンジニアリングへ、実装上の焦点を移している。
  - 人文: 「何を語らせるか」だけでなく「何を忘れさせるか」を設計する点が、編集者や司書の仕事に近い。AI時代の知性は情報を増やす力だけでなく、余計なものを入れない節度にも宿る。

### 3. Don’t be a meat proxy
- 出典: Niklas Gruhnブログ（Simon Willisonが2026-08-03に紹介）
- 日付: 2026-08-03
- リンク: https://gruhn.me/blog/2026-08-03/
- 要約: Slack、PRレビュー、チャットで「Claude said:」としてAI出力をそのまま貼るだけの人を“meat proxy”と呼び、AI出力を読み、理解し、検証し、自分の言葉にして返すことこそ人間が加える価値だと批判する短い記事。Claude Codeでチケットを丸投げし、レビュー指摘もそのまま貼り返す運用では、実装責任がレビューアに移ってしまうと指摘する。
- なぜ面白いか:
  - 技術: LLM出力をワークフローに入れる際の最低限の検証・要約・責任分担を、コードレビューの失敗例として具体化している。
  - 人文: これは単なるAIマナー論ではなく、発話の主体性と労働の帰属の問題である。人間が「中継器」になるほど、会話の信頼や共同作業の倫理が痩せていく。

### 4. Rudder: Prompt based testing and coverage for high-velocity agentic coding
- 出典: GitHubリポジトリ / HN掲載
- 日付: 2026-08-03（HN掲載日。リポジトリページ上の公開日は本調査時点で未確認）
- リンク: https://github.com/RudderCode/Rudder
- 要約: エージェントコーディングで、入力したプロンプトが実際のコード差分にどれだけ反映されたかをテスト・カバレッジ的に測るためのツール。READMEでは、ローカルにプロンプト記録を保持し、Claude/Codex系の文脈処理に渡す際のプライバシー注意も明記している。
- なぜ面白いか:
  - 技術: 「良いプロンプトだったか」を主観で終わらせず、要求と生成コードの対応を測る評価レイヤーとして扱っている。
  - 人文: AI開発の不安は「何が効いたのか分からない」ことから生まれる。プロンプトの足跡を可視化する発想は、創作や設計における作者性、説明責任、学習可能性を取り戻す試みでもある。

### 5. Benchmarks Are Not Validation: A System-Level View of Financial LLM Applications
- 出典: arXiv
- 日付: 2026-07-30
- リンク: https://arxiv.org/abs/2607.28840
- 要約: 金融LLMアプリケーションでは、モデルベンチマークや単発の定性レビューだけでは本番妥当性の証拠にならないとするポジションペーパー。データ、RAG、生成、ツール利用、オーケストレーション、監視、人間へのエスカレーション、ガバナンスまで含めた多層的な検証を求め、LLM-as-a-judgeも複数審査員、ルーブリック、一致度、監査可能性で制御すべきだと述べる。
- なぜ面白いか:
  - 技術: LLM評価をモデル中心のスコアから、検索・ツール・運用・人間介入を含むシステム検証へ拡張している。
  - 人文: 「賢いモデルを選んだ」だけでは社会的責任は果たせない、という制度設計の話になっている。金融の文脈だが、医療、行政、採用など失敗が人に跳ね返る領域すべてに通じる。
