## 今日の一言
AIエージェント時代のDDDは「きれいな設計論」から、エージェントに境界・語彙・判断履歴を守らせるための実行可能な組織言語へ移りつつあります。

## トップ5

### 1. EventCatalog: domains / services / events / schemas をAIエージェントにも読ませるアーキテクチャ台帳
- 出典: GitHub / 公式サイト
- 日付: 2026-08-23 更新（リポジトリ pushed_at: 2026-08-23T15:53:23Z）
- リンク: https://github.com/event-catalog/eventcatalog
- 要約: EventCatalogは、ソフトウェアアーキテクチャ向けのドキュメントツールで、ドメイン、サービス、イベント、スキーマをチームとAIエージェントのために記録することを前面に出しています。DDDそのものを名乗るというより、イベント駆動・境界づけられた文脈・アーキテクチャ可視化を、エージェントが参照できる「生きたカタログ」にする方向性が面白いです。
- なぜ面白いか:
  - 技術: イベント、スキーマ、ドメイン境界を機械可読な台帳に寄せることで、LLM/agentが実装前に文脈と依存関係を確認できる足場になります。
  - 人文: ユビキタス言語は会議室の合意だけでなく、組織の記憶として保存され、次の人間やエージェントへ継承される文化資本になります。アーキテクチャ文書が「監査のための紙」から「共同作業の場」へ戻ってくる流れです。

### 2. DDD-Enforcer: SRSからドメインモデルを作り、PythonコードのDDD逸脱を検出する研究実装
- 出典: GitHub / IEEE DOI付き研究実装
- 日付: 2026-08-13 更新（リポジトリ pushed_at: 2026-08-13T16:50:23Z）
- リンク: https://github.com/barandincoguz/DDD-Enforcer
- 要約: DDD-Enforcerは、PDF/DOCX/TXTの要求仕様から型付きドメインモデルを生成し、Python AST解析、import topology、RAG的トレーサビリティ、複数段LLM推論を組み合わせて、コードがDDDモデルから逸脱していないかをVS Code診断として提示するプロジェクトです。READMEではIISEC 2026のIEEE Xplore論文とDOI（10.1109/IISEC69317.2026.11418529）も示されています。
- なぜ面白いか:
  - 技術: DDDを「設計レビューの助言」ではなく、要求仕様・ドメインモデル・実コードをつなぐ検査パイプラインとして実装している点が強いです。
  - 人文: これはドメインエキスパートの言葉を、後工程で失われない証拠として扱う試みです。仕様とコードのあいだに残る解釈のズレを、個人の記憶や権威ではなく、追跡可能な対話対象に変えています。

### 3. faceto: typed file からイベントストーミングの視覚ボードを作り、LLMと考える
- 出典: GitHub
- 日付: 2026-08-11 更新（リポジトリ pushed_at: 2026-08-11T15:32:08Z）
- リンク: https://github.com/bastien-gallay/faceto
- 要約: facetoは、型付きファイルを入力にして、イベントストーミング用のHTML+SVGボードを生成するRust製ツールです。READMEでは「モデルを指すと、俯瞰できるインタラクティブなボードが得られ、要素ごとに短いメモを書き、次のセッションでモデルを調整する」と説明され、イベントストーミングを起点にコンテキストマップやbounded context canvasへ広げる構想が示されています。
- なぜ面白いか:
  - 技術: イベントストーミングをLLMプロンプトの一過性メモにせず、型付きソースと視覚ボードの往復にすることで、設計探索を反復可能にしています。
  - 人文: ワークショップの価値は、正解を出すことよりも、関係者が「何を事件と呼ぶか」「誰が何に驚くか」を共有することにあります。facetoはその共同思考を、AI相手でも人間同士でも扱える半構造化された場にしようとしています。

### 4. LLM_Ontology_DDD: ユビキタス言語と意味衝突をLLM＋オントロジーで扱う小さな研究リポジトリ
- 出典: GitHub
- 日付: 2026-08-12 作成・更新（created_at: 2026-08-12T12:23:18Z / pushed_at: 2026-08-12T13:50:00Z）
- リンク: https://github.com/BlayTeuR/LLM_Ontology_DDD
- 要約: READMEは短いものの、リポジトリ説明として「Domain-Driven Designにおけるユビキタス言語の構築と意味衝突解決のためのHybrid LLM–Ontology Approach」を掲げています。まだ初期状態ですが、DDDとLLMを単なるコード生成ではなく、語彙・概念・意味の調停に使う方向として注目できます。
- なぜ面白いか:
  - 技術: LLMの柔軟な言語処理とオントロジーの明示的な意味制約を組み合わせると、bounded context間の同名異義・異名同義を検出する設計支援に発展し得ます。
  - 人文: DDDの難所は「言葉が違う」だけでなく、「同じ言葉で別の世界を見ている」ことです。意味衝突を可視化する試みは、組織内の沈黙した対立や専門職文化の違いを、責めずに話し合うための道具になります。

### 5. OOPforge: AI coding agentsにOOP/DDD方言を守らせるハーネス
- 出典: GitHub
- 日付: 2026-08-21 更新（リポジトリ pushed_at: 2026-08-21T00:40:18Z）
- リンク: https://github.com/LooSung/oopforge
- 要約: OOPforgeは「AI ships the feature. OOPforge keeps the architecture.」を掲げ、Java/SpringやPython/FastAPIのバックエンドで、明示的なドメインモデル、use-case境界、レビュー可能なアーキテクチャをAI coding agentに守らせるための方法論パック兼ハーネスです。vibe codingがGod Serviceを生む問題に対して、スキル、ルール、実行例、doctorスクリプトで介入します。
- なぜ面白いか:
  - 技術: LLMに「DDDで書いて」と頼むだけでなく、ルール、参照例、検査、ワークフロー選択をパッケージ化して、エージェントの設計逸脱を運用上の失敗として扱っています。
  - 人文: これはソフトウェア設計を個人の美学ではなく、チームが守る作法として再定義する動きです。AIが速度を上げるほど、組織は「何を速く作らないか」「どの境界を壊さないか」という倫理を明文化する必要があります。
