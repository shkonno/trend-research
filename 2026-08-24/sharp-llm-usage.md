LLM活用の焦点は「賢いプロンプト」単体から、長い文脈を圧縮・分離・検証し、人間の注意と権限をどう設計するかへ移っている。

## トップ5

### 1. Shopify「Gisting」で長いシステムプロンプトを学習済みトークンへ圧縮
- 出典: Shopify Engineering Blog
- 日付: 2026-08-19
- リンク: https://shopify.engineering/gisting
- 要約: ShopifyはSidekick GraphQL agentの約6,000トークンのシステムプロンプトを約1,500のgist tokensへ圧縮し、品質を保ったままTTFTを438msから354ms、エンドツーエンド遅延を6.8秒から4.2秒へ下げたと報告した。長いプロンプトを毎回読ませるのではなく、知識蒸留で特殊トークン埋め込みを学習し、推論時に差し替える実装が詳述されている。
- なぜ面白いか:
  - 技術: 「プロンプトを短く書く」ではなく、プロンプトの振る舞い自体を埋め込みへ蒸留するため、prefix cachingでは消えないdecode時のKV読み出しコストまで下げられる。
  - 人文: 組織の暗黙知や運用ルールが、可読な文章から不可視のトークン列へ移ることで、説明責任と保守性の問いが立ち上がる。LLM時代の「作法」は、文章術であると同時にインフラ設計でもある。

### 2. OneCLI v2: チーム全員にサンドボックス付き個人エージェントを配る設計
- 出典: GitHub README / Launch HN
- 日付: 2026-08-19（Launch HN）、リポジトリ更新 2026-08-23
- リンク: https://github.com/onecli/onecli
- 要約: OneCLIは、社員ごとに隔離されたエージェントを作り、IdP連携、権限ポリシー、シークレット注入、人間承認、Slack接続、永続メモリ、スケジュールを一つのハーネスで扱うOSSプラットフォーム。Launch HNでは「OSS sandboxed agent harness for teams」として紹介され、チーム運用の欠けた部品である権限管理とマルチプレイヤー管理に焦点を当てている。
- なぜ面白いか:
  - 技術: LLMの能力ではなく、サンドボックス、ゲートウェイ、MITMによる認証情報注入、human-in-the-loop承認を組み合わせて、実務利用の失敗モードを外側から制御している。
  - 人文: 「AIを使う個人」から「組織に常駐する個人別エージェント」へ移ると、責任の所在、代理権、監査可能性が日常業務の制度設計になる。これはプロンプトの問題ではなく、職場の権力と信頼の再配置である。

### 3. Proliferate: Claude Code / Codex / OpenCodeを並列に走らせるAI IDE
- 出典: GitHub README / Show HN
- 日付: 2026-08-21（Show HN）、リポジトリ更新 2026-08-23
- リンク: https://github.com/proliferate-ai/proliferate
- 要約: ProliferateはClaude Code、Codex、OpenCode、Cursor、Grokなどをネイティブハーネスで扱い、タスクごとにgit worktree、ブランチ、ターミナル、会話、レビュー状態を分離するOSS AI IDE。並列エージェント、サブエージェント、MCP・スキル・Computer Use・Browser Use連携、定期ワークフローを一つの作業空間にまとめる。
- なぜ面白いか:
  - 技術: 複数エージェントを同じ作業ツリーで競合させず、worktree単位に隔離してレビュー状態を持たせることで、並列化と検証の単位を明確にしている。
  - 人文: これは「一人の賢い相棒」ではなく、小さな作業者群を編集者として采配する感覚に近い。開発者の価値は、コードを書く手から、タスク分解・比較・採用判断を行う編集的判断へ寄っていく。

### 4. Task-CoEvolve: エージェント・ハーネス最適化の検証タスクを適応的に選ぶ
- 出典: arXiv
- 日付: 2026-08-20
- リンク: https://arxiv.org/abs/2608.20169
- 要約: Task-CoEvolveは、モデル重みを変えずにエージェントのハーネスコードを反復改善する際、毎回固定の検証セットを全実行するのではなく、候補ハーネス間で結果が割れる「情報量の高いタスク」を重点的に選ぶ手法。能力境界付近のタスクへ評価コストを寄せ、サンプリング確率を補正して全体性能を推定する。
- なぜ面白いか:
  - 技術: LLM活用の改善ループを「良さそうなプロンプトを試す」から、評価セット自体を共進化させる実験設計へ引き上げている。
  - 人文: 人間の学習でも、すでに解ける問題や全く解けない問題ばかりでは伸びない。AI運用も同じく、境界上の失敗を丁寧に集める文化を持つチームが強くなる。

### 5. PACE: 音声エージェントの「ユーザーが聞いていない文脈」を除去する
- 出典: arXiv
- 日付: 2026-08-07（直近14日より少し古いが、文脈失敗例として重要）
- リンク: https://arxiv.org/abs/2608.07631
- 要約: PACEは、全二重音声対話でサーバー側の生成がクライアント再生より先に進むため、ユーザーが実際には聞いていない発話をモデルが文脈として参照してしまう「Generative Context Mis-anchoring」を扱う。再生境界に合わせてモデル投入文脈を修復するミドルウェアにより、GCM-BenchのReferent Anchoring Accuracyを25.0%から96.3%へ改善したと報告している。
- なぜ面白いか:
  - 技術: コンテキストを「ログに存在する全履歴」ではなく「ユーザーが知覚できた履歴」として再定義し、実時間UIの物理的制約をLLM入力設計へ持ち込んでいる。
  - 人文: 会話の意味は、発話された内容だけでなく、相手が本当に聞いたかに依存する。AI対話でも、共同注意とタイミングを無視すると、礼儀や理解以前に現実の共有が壊れる。
