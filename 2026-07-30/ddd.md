## 今日の一言
AIが実装速度を上げるほど、DDDは「コードの書き方」ではなく、用語・境界・責任を社会的に合意するための設計作法として再浮上している。

## トップ5

### 1. ユビキタス言語をAIエージェント運用の前提にする実践報告
- 出典: X投稿（Yuichi Uemura / @u1）
- 日付: 2026-07-26（UTC）
- リンク: https://x.com/i/status/2081209402502361352
- 要約: CodexなどのAIコーディングエージェントで、曖昧な専門用語が設計全体を崩す問題に対し、設計前に「出典・目的・具体対象・役割・前後関係・候補語・初出定義」を持つ用語表を作る実践が共有されている。特に「名前を付ける前に対象を明確にする（referent-before-label）」というルールが、AIとの継続的なやり取りでユビキタス言語を安定させる鍵になっている。
- なぜ面白いか:
  - 技術: LLMの流暢さによる概念混同を、プロンプト技法ではなくドメイン語彙管理と仕様化のプロセスで抑える実践になっている。
  - 人文: ユビキタス言語は単なる辞書ではなく、チームとAIが「何を同じものとして扱うか」を交渉する文化的な契約になる。AI時代の設計者は、コードを書く人というより、意味の共同体を維持する編集者に近づいている。

  - 人文: 勉強会という形式は、DDDが本来持っていた「会話でモデルを育てる」性質と相性がよい。AI時代の不安は、個人のスキル不足ではなく、共同で意味を作る場の不足として現れている。

  - 人文: 自律的に行為するAIは、システム障害を倫理・法・組織文化の問題へ拡張する。DDDコミュニティがこの問いを扱うのは、ドメインモデルが単に業務を写すものではなく、責任と権力の配置図でもあることを示している。

### 4. OpenDomain: AIエージェント時代の「統治可能な意味インフラ」としてのドメインモデル
- 出典: X投稿（Chase Chou / @janus_path）
- 日付: 2026-07-28（UTC）
- リンク: https://x.com/janus_path/status/2081923201249198512
- 要約: OpenDomainというプロジェクトが、ビジネスドメインモデルを保存・統治するための仕組みとして紹介された。投稿では、DDDの直接的な再実装ではないものの、bounded context、ubiquitous language、core domain modelingと響き合う「AIエージェント時代のdurable, governable semantic infrastructure」として位置づけられている。
- なぜ面白いか:
  - 技術: ドメイン知識を一回限りのプロンプトではなく、長期運用できるセマンティック資産として扱う方向性は、エージェントの記憶・権限・推論の安定性に直結する。
  - 人文: これは企業の知識を誰が定義し、誰が変更でき、AIがどの解釈を正とするかというガバナンスの問題でもある。ドメインモデルは、組織文化の暗黙知を機械可読にする一方で、暗黙知を固定化する危うさも持つ。

### 5. Event StormingをAIファシリテーター化する構想
- 出典: X投稿（Yeongse / @Yeongse_eng ほか関連議論）
- 日付: 2026-07-24（UTC）
- リンク: https://x.com/Yeongse_eng/status/2080590698148139373
- 要約: モブプロ的な壁打ちやBiz/Devの仲裁をAIベースで行い、イベントストーミングのファシリテーター役としてAIが知識を整理・図示・問い返しを行う構想が共有されている。完成された専用OSSはまだ目立たないが、イベント、コマンド、ポリシー、ホットスポット、境界候補を会話から抽出するAI支援は、DDDとエージェント技術の自然な接点になっている。
- なぜ面白いか:
  - 技術: LLMを単なるコード生成器ではなく、ワークショップ状態を保持し、矛盾検出・質問生成・図式化を行うモデリング補助エージェントとして使える。
  - 人文: Event Stormingの価値は、付箋そのものよりも、職能間の認識のズレが露出する瞬間にある。AIファシリテーターは議論を滑らかにする反面、対立や沈黙のような人間的シグナルを消してしまわない設計が問われる。
