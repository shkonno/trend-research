## 今日の一言
Loop engineering は「よいプロンプトを書く技術」から、「止め方・検証・責任の所在まで含む小さな自律システムを設計する技術」へ、一気に言語化が進んでいます。

## トップ5

### 1. Loop engineering: Getting started with loops
- 出典: X投稿（Claude Code / Anthropic系として拡散された長文解説）
- 日付: 2026-06-30（古いが、2026-07下旬のX議論で再参照が集中）
- リンク: https://x.com/i/status/2073047207737983409
- 要約: ループを「目標、成功条件、生成、検証、状態、停止条件」を持つ閉じた反復システムとして整理し、手動の逐次プロンプトから、検証付きで自律的に改善するワークフローへ移る考え方を示しています。特に maker/checker 分離、成功条件と失敗停止条件、状態の永続化、コスト管理が強調されています。
- なぜ面白いか:
  - 技術: ループを単なる `while` ではなく、トリガー、文脈、行動、検証、記憶、停止条件からなる実装単位として定義しており、エージェント運用の設計チェックリストになります。
  - 人文: philosophy の観点では、人間が「作業者」から「制度設計者」へ移る変化を示しています。ethics の観点でも、停止条件と検証を明示することは、自律システムに責任の境界線を引く行為です。

### 2. Loop Engineering / Own the Outer Loop
- 出典: Web記事（Addy Osmani, Elevate / addyo.substack.com）およびXでの再流通
- 日付: 2026-07（直近期間内にXで再流通。Webページ自体は直接取得確認）
- リンク: https://addyo.substack.com/p/loop-engineering / https://addyo.substack.com/p/own-the-outer-loop
- 要約: Addy Osmani は、エージェントが実行の inner loop を回す一方で、人間は判断・承認・結果責任を持つ outer loop を所有すべきだと整理しています。ループ、ハーネス、ソフトウェアファクトリーという語彙で、生成速度より検証・理解・説明責任がボトルネックになる構図を示しています。
- なぜ面白いか:
  - 技術: ハーネス、サンドボックス、権限、永続メモリ、観測性、CIなどをループの外枠として扱い、単体エージェントではなく運用可能な生産システムとして考えています。
  - 人文: history の観点では、1960年代からの「ソフトウェア工場」構想をAIエージェント時代に再解釈している点が興味深いです。ethics の観点では、暗い工場のように人間不在で成果物が増える時代に、誰が理解し、誰が責任を負うのかを問います。

### 3. ループエンジニアリングをどう始めるか
- 出典: Web記事（btnopen.com、日本語技術記事）/ X共有
- 日付: 2026-07-29（X共有日。記事本文は直接取得確認）
- リンク: https://www.btnopen.com/posts/lean-loop-engineering
- 要約: 日本語圏での実践例として、ボードゲーム用コンパニオンアプリ開発を題材に、スマートフォンからタスク投入し、AIエージェントが要件を磨き、PRを作り、人間がレビューしてマージするという開発サイクルが紹介されています。3日弱で約50件のPRをマージした実例から、内側の「コーディングのループ」と外側の「エンジニアリングのループ」を分けて考える点が有用です。
- なぜ面白いか:
  - 技術: MCPやAgent Skillsなどの道具・状態を渡すインターフェースが整い、コード生成だけでなく要件、設計、テスト、レビュー、PR運用までを小さくループ化できることを示しています。
  - 人文: anthropology の観点では、開発者の日常的な身体性が「MacBookを開く」作業から「スマホで依頼し承認する」作業へ移る生活文化の変化が見えます。creativity の観点でも、個人の趣味プロジェクトが小さな自動化工房になる点が魅力的です。

### 4. When Do Agent Loops Mistake Stagnation for Progress?
- 出典: arXiv論文 / Xでの研究紹介
- 日付: 2026-07-27
- リンク: https://arxiv.org/abs/2607.25152
- 要約: Hyundoo Park と Byungho Choi による論文で、長時間動く自律LLMエージェントが自己評価だけで進捗を判断すると、実際には停滞や退行を「改善」と誤認する progress mirage が起きると報告しています。54サイクル中、エージェントは毎回改善を主張した一方で、56%は実測上ゼロ以下の進捗であり、強い in-band judge でも現実世界の回帰を十分には防げませんでした。
- なぜ面白いか:
  - 技術: ループ内の自己評価を強いモデルに置き換えるだけでは不十分で、成功信号が transcript の外にある場合は、外部世界に接続された検証器が構造的に必要だと示しています。
  - 人文: philosophy の観点では、「進歩している」という自己物語と、世界の状態としての進歩がずれる問題を扱っています。ethics の観点では、自律ループの成果を誰が、どの根拠で承認するのかという監査可能性の問題に直結します。

### 5. ループの次はグラフか：Graph engineering への移行論
- 出典: X投稿（日本語・英語の議論）/ Zenn記事共有
- 日付: 2026-07-29
- リンク: https://x.com/horikoshikatsum/status/2082603673910493450 / https://zenn.dev/jodycraft/articles/dfe38e73e1ef8a
- 要約: 日本語Xでは「ループエンジニアリングの次は本当にグラフなのか」という議論が出ており、英語圏でも単一エージェントの act→observe→adjust ループから、Planner、Researcher、Writer、Reviewer など複数ノードを明示的に結ぶ graph engineering へ関心が移っています。ループは探索に、グラフは再現性・並列化・チェックポイント管理に向くという整理が目立ちます。
- なぜ面白いか:
  - 技術: 失敗した箇所だけを再実行できる状態機械・DAG・LangGraph的な設計へ移ることで、長い単一コンテキストに依存するループの脆さを減らせます。
  - 人文: narrative の観点では、万能な一人のAI労働者という物語から、役割分担された組織・工場・編集部の物語へ想像力が移っています。history の観点でも、分業と工程設計という古典的な産業史の発想がAIエージェント設計に戻ってきています。
