## 今日の一言

AIエージェント時代のDDDは、「コードを書く技法」よりも、仕様・言語・境界・意思決定をどこでAIに読ませるかを設計する組織技法へ寄っている。

## トップ5

### 1. ADRとユビキタス言語を、AIにいつ効かせるか

- 出典: Qiita / ikeyansaza
- 日付: 2026-07-19
- リンク: https://qiita.com/ikeyansaza/items/490979a2aec38f90d47b
- 要約: AIエージェントにADRやユビキタス言語を「置いておけば読んでくれる」と期待せず、issue起票時・実装時・レビュー時のどこで差し込むかを人間が設計すべきだと整理している。テストはCIで強制的に効く一方、ADRとユビキタス言語は読まれる経路を設計しないと置物になる、という問題設定がDDD実践に直結する。
- なぜ面白いか:
  - 技術: DDDの言語資産を、LLMコンテキストへ静的注入するか動的取得させるかという「コンテキストエンジニアリング」の設計問題として扱っている。
  - 人文: ユビキタス言語を単なる用語集ではなく、組織内の古株が果たしていた「あ、それは確認した方がいい」という文化的媒介として捉え直している。AI導入後も、知識が誰に・いつ・どう届くかという社会的設計が残る点が重要。

### 2. faceto: typed file → visual workshop board with an LLM

- 出典: GitHub / bastien-gallay/faceto
- 日付: 2026-07-26 更新（リポジトリ更新日）
- リンク: https://github.com/bastien-gallay/faceto
- 要約: 型付きファイルからイベントストーミングのHTML/SVGボードを生成し、各要素にメモを付けて次のLLMセッションでモデル調整に使うツール。READMEでは「Event storming is the first board format」と明記され、C4、ストーリーマッピング、インパクトマッピングへの拡張も示唆されている。
- なぜ面白いか:
  - 技術: イベントストーミングをLLMとの往復可能な構造化ファイルに落とし、会話・図・次回プロンプトを接続する軽量なDDDワークベンチになっている。
  - 人文: ワークショップの付箋は本来、参加者の記憶や交渉の痕跡を残す媒体だったが、それをAIが読める形式へ変換している。対面の共同理解と機械可読なモデルの境界をどうつなぐか、という新しいファシリテーション論として読める。

### 3. 開発プロセスの再構築 ～実装工程の価値低下（AIエージェント時代のソフトウェア設計）

- 出典: Qiita / mellowlaunch
- 日付: 2026-07-25
- リンク: https://qiita.com/mellowlaunch/items/9a0613fdc4470e1f4aef
- 要約: AIによるコード生成で実装がクリティカルパスではなくなり、価値が「何を作るか」「どのようなドメイン知識を持つか」「全体をどう設計するか」へ移ると論じる記事。コードは固定的な資産ではなく、仕様から再生成されるアウトプットへ近づくという見立てが示されている。
- なぜ面白いか:
  - 技術: 実装コスト低下後のボトルネックをドメイン理解・仕様・構造設計に置き直しており、DDDの戦略設計がAI時代に再評価される理由を説明している。
  - 人文: 「コードを書く人」の職能アイデンティティが、「問題を定義し、言語を整える人」へ移るという職業文化の変化を捉えている。DDDがエンジニアリング技法であると同時に、組織の価値判断を可視化する作法であることが浮き上がる。

### 4. Automating Domain-Driven Design: Experience with a Prompting Framework（古いが関連度高）

- 出典: arXiv / cs.SE, cs.AI
- 日付: 2026-03-27（直近14日外）
- リンク: https://arxiv.org/abs/2603.26244v1
- 要約: LLMでDDD活動を自動化するプロンプティング・フレームワークを提案し、ユビキタス言語、イベントストーミング、境界づけられたコンテキスト、集約、技術アーキテクチャへの写像という5段階に分解して検証している。前半の言語化・文脈整理は有用だが、後半の集約や実装アーキテクチャでは小さな誤りが蓄積して実用性を損なう、と報告している。
- なぜ面白いか:
  - 技術: LLMを「DDDの完全自動化装置」ではなく、ユビキタス言語とコンテキストマップのたたき台を作る協調相手として位置づけ、どこから専門家判断が不可欠になるかを示している。
  - 人文: DDDの核心が、正解を生成することではなく、関係者がトレードオフを話し合える共通物を作ることだと再確認させる。AIが議論の前処理を担うほど、人間側の判断責任と対話の質が目立つ。

### 5. The Method: agentic refinement layer for AI coding agents（古いが関連度高）

- 出典: GitHub / nlawstudio/ai-refinement-method
- 日付: 2026-06-24 更新（直近14日外）
- リンク: https://github.com/nlawstudio/ai-refinement-method
- 要約: 「vibe coding」ではなく「vibe spec'ing」として、自然言語の意図からドメイン探索、意思決定、脅威モデル、受け入れ基準、失敗するテストを含む実装可能なストーリーへ落とすマルチエージェント手法。READMEでは、イベントストーミング、DDD、リファインメントが、AIコーディングの上流で仕様品質を高める方法として位置づけられている。
- なぜ面白いか:
  - 技術: コーディングエージェントに直接実装させる前に、DDD的な探索とテスト可能な受け入れ条件を生成する「仕様レイヤー」を置いている点が実践的。
  - 人文: 安く大量にコードが作れる時代に、問いを荒く出してもよいのか、誰が仕様の著者なのか、という責任の問題を前景化している。AIを代筆者ではなく、弱い推論に抵抗するファシリテーターとして使う発想が面白い。
