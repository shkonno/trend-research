## トップ5

### 1. White Box Evidence Packages for Policy Audit Reports
- 出典: arXiv
- 日付: 2026-07-23
- リンク: https://arxiv.org/abs/2607.21462
- 要約: LLM生成の政策監査レポートが本当に根拠に支えられているかを、証拠インターフェースを変えて比較した研究です。内部証拠を多く引用しても妥当性が自動的に上がるわけではなく、無関係な証拠でももっともらしく見えるという監査上の危険を示しています。
- なぜ面白いか:
  - 技術: 「証拠を出させる」だけでなく、証拠の関連性・使われ方・レビュー可能性を評価単位にする点が、RAGや監査ワークフローの実装に直結します。
  - 人文: 透明性は情報量の多さではなく、読み手が責任を持って判断できる配置の問題だと分かります。AI監査は、モデルの内面を覗く神話よりも、制度的に検証できる証拠設計へ寄っていきそうです。

### 2. Capital Markets LLM Reliability Score (CM-LRS): From Plausible to Bankable
- 出典: arXiv
- 日付: 2026-07-23
- リンク: https://arxiv.org/abs/2607.21340
- 要約: 資本市場のLLMワークフローを、単なるQA正答率ではなく、事実性、証拠追跡性、数値整合性、ワークフロー完全性、レビュー可能性など7軸で評価するスコアを提案しています。論文のキーワードは「plausible ではなく bankable」で、規制・取引相手に耐える成果物を測る設計です。
- なぜ面白いか:
  - 技術: 業務で使えるLLM評価を「回答」ではなく「提出物・レビュー・監査」の層に引き上げているため、実運用の評価表として再利用しやすいです。
  - 人文: ここで問われているのは知能の高さより、信用できる書類文化に参加できるかです。LLM活用は効率化ではなく、組織が何を根拠として意思決定するかの再設計になっています。

### 3. PoTRE: Test-Time Reasoning inspired by Cognitive Heterogeneity
- 出典: arXiv
- 日付: 2026-07-22
- リンク: https://arxiv.org/abs/2607.20268
- 要約: 単一の推論ストリームではなく、敵対的改善、階層的計画、スペクトラム探索、直接チェーンという異なる推論エージェントを分け、最後にタスク適応的に統合する枠組みです。難問ベンチマークで、均質な推論を単純に厚くするより少ないまたは同程度のトークンで性能向上を狙っています。
- なぜ面白いか:
  - 技術: 「よいプロンプトを一発で書く」から、「異なる失敗モードを持つ推論役を並べて統合する」へ、プロンプト設計を小さな認知アーキテクチャとして扱っています。
  - 人文: 人間のチームでも、批判者・計画者・探索者・実行者を分けると議論の質が変わります。LLM活用の鋭さは、万能な人格を作ることではなく、複数の不完全な視点をどう編成するかにあります。

### 4. Grounded verification of chemical and materials reasoning: detection is the bottleneck
- 出典: arXiv
- 日付: 2026-07-19
- リンク: https://arxiv.org/abs/2607.17417
- 要約: 化学・材料分野でLLMがもっともらしい分子式や物性値を捏造する問題に対し、検証可能な主張を抽出し、権威あるデータベースや物理制約でチェックして修正する研究です。修正自体は機能するが、制約になるのは誤りを検出できるかどうかだと報告しています。
- なぜ面白いか:
  - 技術: 全文検索を増やすより、チェック可能な主張の抽出、スコープ設定、ゲート付き修正ループを作る方が、コストと信頼性の両面で実践的です。
  - 人文: 「AIの答えを信じるか」ではなく、「どの主張が共同体の知識体系に照合可能か」を問う姿勢が重要です。専門家の役割は消えるのではなく、検証可能性の境界を設計する側へ移ります。

### 5. Ask HN: How are you LLM-coding in an established code base?（古いが実践的）
- 出典: Hacker News / Algolia API
- 日付: 2025-12-16（直近14日外だが、実務失敗例として関連）
- リンク: https://news.ycombinator.com/item?id=46292682
- 要約: 既存の大規模コードベースでLLMコーディングをどう使うかという実務者の議論です。コメントでは、単体テストのように検証が容易なタスクでは有効だが、巨大なレガシーコードや複雑な相互作用ではコンテキスト不足で「むしろ役に立たない」場面がある、という経験が共有されています。
- なぜ面白いか:
  - 技術: LLMに任せる範囲を「生成が簡単」ではなく「人間が安く検証できる」単位へ切る、という実務上かなり鋭いヒューリスティックが見えます。
  - 人文: これはAIへの失望談ではなく、道具と職人技の境界線を引き直す話です。レガシーシステムの知はコード断片ではなく、歴史的経緯や暗黙の運用知に宿るため、LLM活用はその記憶をどう外部化するかにかかっています。
