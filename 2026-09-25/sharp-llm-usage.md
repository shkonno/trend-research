### 1. Claude Code Best Practices: 検証手段・探索→計画→実装・CLAUDE.md・サブエージェント
- 出典: Anthropic / Claude Code Docs
- 日付: 2026-09-24（ページ取得時点で確認）
- リンク: https://www.anthropic.com/engineering/claude-code-best-practices
- 要約: Claude Codeのベストプラクティスとして、「Claudeに作業を検証する方法を与える」「まず探索し、計画してからコードを書く」「具体的な文脈を与える」「CLAUDE.mdでプロジェクト知識を保存する」「調査用サブエージェントや敵対的レビューを使う」といった運用パターンが整理されている。CLIエージェントを“会話相手”ではなく、テスト・権限・フック・サブエージェントを持つ作業環境として扱う発想が中心。
- なぜ面白いか:
  - 技術: LLM活用の品質を、プロンプト単体ではなく、検証コマンド、文脈ファイル、権限設定、並列セッション、レビュー手順まで含むハーネス設計として定義している。
  - 人文: 「AIに任せる」と「人間が責任を持つ」の境界が、会話文ではなく作業制度として設計され始めている点が重要。熟練者の勘を、CLAUDE.mdやチェックポイントのような共有可能な作法へ翻訳している。

### 2. Can LLMs Reason About Runtime Behavior? SWE-Fluxが示す“実行理解”の壁
- 出典: arXiv
- 日付: 2026-09-23
- リンク: https://arxiv.org/abs/2609.28449
- 要約: SWE-Fluxは、12の実Pythonリポジトリから480件の実行根拠付き問題を作った、リポジトリレベルの動的実行推論ベンチマーク。5つのLLMを評価したところ、最良モデルでも正答率は37%にとどまり、単純な局所的挙動よりも、データフロー、手続き間の状態、テストスイート全体の集約に弱いことが示された。
- なぜ面白いか:
  - 技術: コードLLMの弱点を「読めるが、走った時の状態を追えない」と切り分け、LLM評価をLLM判定ではなく計測済み実行結果に接続している。
  - 人文: これはAIコーディングの過信に対するよい解毒剤で、開発者に“実行という現実”へ戻る習慣を促す。AI時代の読み書き能力は、自然言語とコードだけでなく、テストログや状態変化を読む能力へ広がっている。

### 3. Harness as a Language: 最小エージェントループに制約・監視・再帰を載せる
- 出典: arXiv
- 日付: 2026-09-22
- リンク: https://arxiv.org/abs/2609.26891
- 要約: JAZという最小主義のLLMエージェントフレームワークを提案し、LLMが任意の実行コードと再帰的invokeを使える一方で、入力・出力・ツール・制約・監視をプログラム可能にする。メモリや自己改善のような専用機構を増やす前に、エージェントループそのものを“言語”として表現できるかを検討している。
- なぜ面白いか:
  - 技術: エージェント活用を、巨大なフレームワークではなく、invoke、フック、制約、観測可能性の組み合わせとして再構成している。
  - 人文: 道具が複雑になるほど、人間は「何が起きているか」を見失いやすい。最小構成から表現力を立ち上げる姿勢は、AIに仕事を委ねる時代の“透明な制度設計”として読める。

### 4. Spectra: KYC業務をルールエンジン＋LLMで再編する実務パイプライン
- 出典: arXiv
- 日付: 2026-09-21
- リンク: https://arxiv.org/abs/2609.25474
- 要約: 金融のKYCオンボーディングで、文書分類、構造化抽出、コンプライアンス検証を、ルールエンジンとLLMエージェントで組み合わせるSpectraを提案。単に既存業務へLLMを差し込むのではなく、4者間の逐次ハンドオフを2者中心に再構成し、遅延や引き継ぎの摩擦を減らす設計になっている。
- なぜ面白いか:
  - 技術: LLMの曖昧な推論に、明示的な規制ルールと検証ステップを重ねることで、業務自動化を“生成”ではなく“分類・抽出・検証のパイプライン”として実装している。
  - 人文: ここでの本質は人員削減ではなく、責任と判断の流れをどう作り直すかにある。ハンドオフの削減は効率化であると同時に、誰が何を確認したのかという組織の記憶を再設計する行為でもある。

### 5. A Tutorial on Prompt Engineering: 雑な思考をAIワークフロー仕様へ変換する
- 出典: arXiv
- 日付: 2026-09-05（直近14日より少し古いが関連性が高いため採用）
- リンク: https://arxiv.org/abs/2609.22249
- 要約: プロンプトエンジニアリングを、思いつきの質問ではなく、作業定義、必要な文脈の選別、役割や複数視点の設定、肯定的な品質目標、批判・プレモーテム・検証を含むワークフロー設計として整理するチュートリアル。Occamの剃刀やChekhovの銃を応用し、不要な指示を減らす考え方も提示している。
- なぜ面白いか:
  - 技術: 役割付与や禁止事項の羅列よりも、文脈の最小化、品質基準、批判的検証、エスカレーション境界を重視しており、実務プロンプトの失敗を減らす設計原則として使いやすい。
  - 人文: “よい問い”を作る能力が、AI時代の基礎教養になっていることを示している。人間の曖昧な意図を、機械に渡せる仕様へ変える過程は、翻訳であり、編集であり、自己理解でもある。
