## 今日の一言
Loop engineering は「プロンプトの巧拙」から、観察・停止条件・監査・人間の責任を組み込む反復的な実践知へ移りつつあります。

## トップ5

### 1. Loop Engineering: Building Blocks, Adoption, and Impact
- 出典: arXiv
- 日付: 2026-08-22（v2: 2026-08-26、直近14日より古いが基礎文献として重要）
- リンク: http://arxiv.org/abs/2608.21884
- 要約: エージェントを対話的に促すのではなく、スケジュールやリポジトリイベントでエージェントを起動し、機械的に検証可能な条件で停止させる「loop engineering」を、構成要素・採用状況・影響から整理した論文。実務者の流行語を、ハーネス、イベント、チェック、終了条件という工学的単位に分解している点が重要です。
- なぜ面白いか:
  - 技術: ループを「開始条件・実行環境・評価・停止条件」の設計問題として定義し、エージェント運用を再現可能なシステム設計へ引き上げています。
  - 人文: これは認識論的には「いつ知ったと言えるのか」を、会話の納得ではなく検証可能な停止条件へ移す動きです。実践知の観点では、熟練者の勘を単なる暗黙知にせず、反復可能な作法として外部化する試みでもあります。

### 2. Towards Agentic Cloud Engineering: Graph and Loop Engineering with a Zero-Trust Agent Harness
- 出典: arXiv
- 日付: 2026-08-30（直近14日より古いが関連性が高いため採用）
- リンク: http://arxiv.org/abs/2609.00050
- 要約: クラウド運用タスクを、グラフとループ、ゼロトラスト・ハーネス、検証済みデプロイとして扱うエージェント型クラウドエンジニアリングの枠組み。自律エージェントにツール実行・失敗回復・完了検証を任せるには、実行権限と観測可能な証拠をセットで設計する必要があると示しています。
- なぜ面白いか:
  - 技術: ループをクラウド変更の実行制御・権限境界・完了検証に接続し、エージェント運用をゼロトラストな制御系として扱っています。
  - 人文: サイバネティクス的には、これは「目的をもつ主体」ではなく「観測とフィードバックで制約される行為者」としてAIを見る転換です。責任の所在も、モデルの内面ではなく、ハーネスと証跡の制度設計へ移ります。

### 3. crt — Code Review Tool for agent-written code
- 出典: GitHub / Hacker News（Show HN）
- 日付: GitHub作成 2026-03-30、更新 2026-09-21、push 2026-09-18（直近約14日に近い更新）
- リンク: https://github.com/imron/crt
- 要約: `crt` は、エージェントが書いたコードを人間または別エージェントがレビューし、コメントをMCP経由でエージェントへ戻して修正させるためのローカルなコードレビュー道具。READMEは「AIが高速にコードを書く時代だからこそ、人間が理解し責任を持つレビューの場が必要」と明確に述べています。
- なぜ面白いか:
  - 技術: 生成→レビュー→コメント→修正という人間参加型ループを、PRやチャットではなく、エージェントが直接読める構造化された作業面にしています。
  - 人文: ここでは人間は単なる承認ボタンではなく、理解し責任を負う解釈者です。実践知は「全部自動化する」方向ではなく、反復のどこで人間の判断を残すかという職能倫理として現れています。

### 4. OpenAPPA — deterministic guardrails that track flows
- 出典: Web / Hacker News（Show HN）
- 日付: 2026-09-28（HN掲載確認）
- リンク: https://www.openappa.com/
- 要約: OpenAPPA は、LLMによる二次判定ではなく、ツール呼び出しをまたいだデータフローを追跡する決定的ガードレールを掲げるプロジェクト。サイトでは、非決定的な承認・判定モデルはツール横断の情報流を追えないため、エージェントを壊さずに制御するにはフロー追跡が必要だと主張しています。
- なぜ面白いか:
  - 技術: ループ内の各ツール実行を孤立したイベントではなく、情報の流れとして検証するため、プロンプトインジェクションやデータ持ち出しに対する制御点が増えます。
  - 人文: これは「信頼」をモデルの善意や賢さから切り離し、制度・境界・手続きとして作る発想です。サイバネティクスの語彙で言えば、自由な行為を許すためにこそフィードバック制御と観測可能性が必要になる、という逆説が見えます。

### 5. Epistemic Warrant for LLM Recommendations: Characterizing the Basis for Reliance When Ground Truth Is Unavailable
- 出典: arXiv
- 日付: 2026-09-03（直近14日より古いが哲学的関連性が高いため採用）
- リンク: http://arxiv.org/abs/2609.04127
- 要約: 正解が直接得られない意思決定で、LLMの個別推薦にどの程度依拠してよいかを「epistemic warrant（認識論的保証）」として定式化する論文。信頼一般や平均的性能ではなく、特定の推薦がどの範囲で安定しているかを扱う点が、ループの検証思想とつながります。
- なぜ面白いか:
  - 技術: ループ評価を単なる成功率ではなく、推薦の安定性・適用範囲・依拠可能性の測定へ拡張する視点を与えます。
  - 人文: loop engineering の核心は、AIの答えを「信じる」ことではなく、どの条件なら依拠してよいかを問う認識論です。これは古典的な証言・信頼・実践的推論の問題が、LLMエージェントの運用現場に戻ってきた例です。
