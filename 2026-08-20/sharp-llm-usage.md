## トップ5

### 1. 2026年のコンテキストエンジニアリング
- 出典: Web記事（ASI.TOKYO、Towards AI動画/記事の日本語紹介）
- 日付: 2026-08-18
- リンク: https://asi.tokyo/2026/08/18/2026%E5%B9%B4%E3%81%AE%E3%82%B3%E3%83%B3%E3%83%86%E3%82%AD%E3%82%B9%E3%83%88%E3%82%A8%E3%83%B3%E3%82%B8%E3%83%8B%E3%82%A2%E3%83%AA%E3%83%B3%E3%82%B0-louis-francois-bouchard%E3%80%81omar-sola/
- 要約: AIチューターを題材に、会話全体保持、要約、コンパクション、RAG、BM25、ハイブリッド検索、プロンプトキャッシュ、ローカルモデルを比較している。安易な圧縮が常に正解ではなく、長大コンテキストでも測定次第では記憶性能や検索性能を維持できる、という実践的な示唆が中心。
- なぜ面白いか:
  - 技術: コンテキスト削減を信仰せず、品質・速度・コスト・記憶性能を測ってから保持/検索/圧縮を選ぶ設計論になっている。
  - 人文: 「忘れるAI」をどう補うかではなく、「何を覚えさせ続けるべきか」という記憶の政治学に近い問題を扱っている。教育・チュータリング用途では、効率よりも学習者との履歴をどう尊重するかが問われる。

### 2. agent-flow: プロジェクトに反復可能なエージェント作業型を敷くCLI
- 出典: GitHubリポジトリ（nothingnesses/agent-scaffold、crate名 agent-flow）
- 日付: 2026-08-18更新（作成: 2026-07-09）
- リンク: https://github.com/nothingnesses/agent-scaffold
- 要約: AGENTS.md、計画テンプレート、再利用可能なプロンプトをプロジェクトに配置し、「コンテキストを前倒しする→構造化計画を書く→レビュー→小さく実装→レビュー」というワークフローを毎回再現するためのRust製CLI/TUI。既存リポジトリに導入しても作業ファイルを上書きしない設計が強調されている。
- なぜ面白いか:
  - 技術: 個人のプロンプト術を、リポジトリ内の標準手順・計画文書・レビュー導線として固定化している点が実用的。
  - 人文: 「AIをどう使うか」を個人芸からチームの作法へ移す試みで、暗黙知を共同体の儀式に変える動きに見える。エージェント時代の開発文化は、速さよりも作業の可読性で差がつき始めている。

### 3. Prompt-Literate Workflow: LLM出力を候補成果物として扱うリテラルな開発プロセス
- 出典: GitHubリポジトリ（IRONCREED/prompt-literate-workflow）
- 日付: 2026-08-12更新（作成: 2026-06-03）
- リンク: https://github.com/IRONCREED/prompt-literate-workflow
- 要約: 人間が書いたリテラルな計画を真のソースとし、チャンク契約、境界付きプロンプト、LLM生成候補、レビュー、テスト/スモークチェック、TRACE、受け入れ済み更新という流れを定義する。LLM出力をビルド成果物のように自動採用せず、検証と追跡可能な受け入れを必須にする点が核心。
- なぜ面白いか:
  - 技術: 生成結果を「候補」と明示し、契約・テスト・TRACEを挟むことで、LLM利用を決定論的な検証パイプラインに接続している。
  - 人文: これはプロンプトの上手さではなく、責任の所在を保存するための書記術である。AI時代の開発者は、書く人から「受け入れを記録する編集者」へ役割が広がっている。

### 4. untrusted contentを読むエージェントは隔離せよ、というX上の実践メモ
- 出典: X投稿（DuckDuckGo経由で確認、@seeconvm）
- 日付: 2026-08-06
- リンク: https://x.com/seeconvm/status/2085223514487877778
- 要約: サポートチケット、スクレイピングページ、ユーザーフィードバック、サードパーティAPI応答など、自分が書いていない内容を読むワークフローはプロンプトインジェクション源として扱うべきだと指摘。対策として、未信頼コンテンツを読むエージェントには書き込み権限や高権限アクションを持たせない「隔離」を提案している。
- なぜ面白いか:
  - 技術: 入力検証だけでなく、読み取り役と実行役を権限分離することで、LLMワークフローの失敗半径を小さくしている。
  - 人文: これはAIを「賢い秘書」と見るより、「噂や指示に影響される組織内アクター」と見る発想に近い。信頼できない言葉に触れた者へどこまで権限を与えるか、という制度設計の問題でもある。

### 5. PACE: 音声対話LLMの「聞いていない文脈」を修復するPlayback-Aligned Context Engine
- 出典: arXiv
- 日付: 2026-08-07
- リンク: https://arxiv.org/abs/2608.07631
- 要約: フルデュプレックス音声対話では、サーバが生成した応答がクライアントで再生される前に会話状態へ入ってしまい、ユーザーが実際には聞いていない内容を前提に次の発話が解釈される失敗（Generative Context Mis-anchoring）が起きる。PACEは、クライアントの再生境界に合わせてモデル向けコンテキストを調整し、中断後に未再生部分を除外・修復するミドルウェアを提案する。
- なぜ面白いか:
  - 技術: LLMのコンテキストを「生成済みトークン」ではなく「ユーザーが経験した可能性のある状態」に同期させる、実運用ならではの鋭い失敗対策である。
  - 人文: 会話とはログの列ではなく、相手が実際に聞いたことの上に成立する共同作業だと示している。音声AIの礼儀や責任は、モデル内部の整合性よりも人間側の体験時間に合わせる必要がある。
